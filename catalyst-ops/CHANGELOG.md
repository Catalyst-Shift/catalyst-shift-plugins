# Changelog — catalyst-ops

## 0.5.0 — 2026-10-03

- `/next` catches up with how nourish-enablement and lbl-nextjs run the loop (CAT-948). A repo's own loop (`.claude/commands/next.md`, or CLAUDE.md "How work moves" / "How we ship") wins, and in nourish its attack steps replace gstack, so a missing `/codex` there no longer sends a card to Blocked (HOW_WE_BUILD §3's client-repo exception). Cards belong to "the person running the loop": a card assigned to someone else is never taken, the claim is assign + In Progress after re-reading the card, and hard-stop yeses come from whoever the repo's CLAUDE.md names (nourish D38: Kevin or Keith), recorded by name. Preflight runs the repo's own merge-gate script where there is one, and the PR state is checked once after arming auto-merge. Big cards split across PRs with `Refs` / `Closes` and a Deferred section. Parallel sessions: one worktree per card, no bare `git stash`, a collision check against In Progress cards, shared counters (version, migration number) taken against fresh `origin/main`, and `gh pr update-branch` on a strict-ruleset repo only when the PR is otherwise ready. CI-fail handling describes verdict reuse (CAT-785, CAT-947). Deep-path detection reads lbl's `deep-paths.txt`. The repo table names the GitHub repo `nourish-enablement` (CAT-794).
- CONTRIBUTING describes the PR + auto-merge flow; no more direct pushes to `main`.

## 0.4.1 — 2026-09-29

- `/next`: preflight (before the first card and before each auto-merge) stops the loop unless `main` enforces `adversarial review` from GitHub Actions in a ruleset the merging identity can't bypass. Checklist lines state outcomes, never tool names, with evidence the CI reviewer can read. gstack is the in-session method, not a gate (every-card / when-it-fits / not-in-/next table). A missing gstack skill means getting the same outcome another way, noted in the PR body, never Blocked, except the canon's §3 attack steps (`/review`, the cross-model adversarial pass, `/cso` on deep paths) and `/careful` on deep paths. A missing, failed, early-stopped or partial §3 run means Blocked, and §3 re-runs on anything edited after it. Deep-path detection uses every path the PR can carry (committed since the merge base, staged, unstaged, untracked; renames off; pipefail) and treats any error as deep. The version and CHANGELOG bump happens before the last §3 pass. After a CI review fail, fix every blocking finding, re-run §3, and push once; an infrastructure-only fail is re-run (or, where the token can't re-run, retried with an empty commit) and still counts toward the three fails; the fail comment must match the current head and the failed run attempt. (CAT-783)
